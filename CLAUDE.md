## What this project is

A data visualization project originally built for a university course (CSCE 567, Visualization
Tools), now being repackaged as a portfolio piece linked from a software engineering resume
(new-grad SWE applications). Hosted on GitHub Pages from the repo root; `index.html` is the
landing page.

**Stack:** Python + Pandas + Plotly Express (chart generation) -> static HTML/CSS (site).
No build step, no backend, no package manifest, no tests. Charts are pre-generated by running
Python scripts by hand; the output HTML is then hand-edited and committed.

**What it does:** cleans and merges three inconsistently-formatted U.S. Census/election `.xlsx`
exports into tidy dataframes, then produces 7 interactive Plotly charts on voter turnout vs.
income vs. race/demographic group, 1978-2024, with emphasis on the 2024 election.

**Audience for the current refresh:** SWE recruiters skimming a resume link for 15-30 seconds --
not an academic audience. Make it read as a polished portfolio artifact without misrepresenting
what it is.

## Architecture

Three-stage manual pipeline, with a human step between each stage:

```
data/*.xlsx  --[reformatData/*.py]-->  data/*.csv  --[visualization*/*.py]-->  visualization*/*.html
                (mostly disabled)        (committed)                            (hand-edited after)
```

**Stage 1 -- `reformatData/`** turns irregular Census `.xlsx` exports into the tidy CSVs in
`data/`. The interesting logic is in `reformatA2.py`: `tableA2.xlsx` interleaves year rows and
race header rows in the same column, so it regex-matches `^\s*(\d{4})` to split year from race and
forward-fills the race label down. Each script also renames positional columns (`0`, `1`, `2`, ...)
to real names and slices out header/footer junk by hardcoded row index.

**Two of these three scripts have their `to_csv` write commented out** (`reformatA2.py`,
`reformatHst.py`) -- running them only prints. `reformatVote07.py` still writes live to
`../data/incomeVote.csv`. Since `data/` is off-limits (see Constraints), do not run
`reformatVote07.py` casually.

**Stage 2 -- `visualization{One,Two,Three}/*.py`** read the committed CSVs and emit chart HTML.

- `visualizationOne.py` -> 2 line charts (voting % over time; median income over time, both by race)
- `visualizatinoTwo.py` -> 3 animated scatter plots (income vs. voting %, split all-years /
  primary-years / midterm-years, animated by `Year` with a slider). Builds `combinedDf`, the inner
  merge of income and vote data on `['Race', 'Year']` -- this is the dataframe to use for any
  income-vs-turnout statistic. Also dumps `combined.csv`, which nothing else consumes.
- `visualizationThree.py` -> 3 bar charts for 2024 only (turnout by income bracket; turnout by race;
  income distribution by race)

Shared conventions across all three: `plot_bgcolor='black'`, `font_family='balto'`,
`title_font_size=30`, `px.colors.qualitative.G10`, and a custom `hovertemplate` per trace.
The first `to_html` call in each file uses `include_plotlyjs='cdn'` and the rest use
`include_plotlyjs=False`, so all charts in one file share a single CDN load -- preserve that
pattern when adding or reordering figures.

The income-parsing block in `visualizationOne.py` and `visualizatinoTwo.py` is duplicated verbatim,
including a hand-tuned walk over `rawIncomeDf` with hardcoded index ranges (`i < 23`, `23-46`, ...)
and explicit skips for the duplicate 2013 and 2017 Census rows. It is fragile and deliberately out
of scope to refactor.

`visualizationThree.py` uses `px.histogram` for what is actually a bar chart -- a leftover from an
earlier design, flagged in a comment in the file. Not a bug.

### The generated HTML files are hand-edited after generation

This is the most important thing to know before running any chart script.

`lineCharts.html`, `scatterPlots.html`, and `visualizationThree.html` are **not** what the Python
scripts write. Plotly emits bare fragments (`full_html=False`), and someone then hand-added, in the
committed files:

- a `<head>` linking `../styles/visualization.css`, plus `<body>` / `</body>` tags
- an `<a class="return" href="../index.html">return to home page</a>` link at the top
- interpretive `<p>` and `<p class="note">` paragraphs **interleaved between the chart divs**, not
  merely appended at the end
- reindented, human-formatted markup

**This is no longer a hazard as of the Pearson-correlation pass.** Each script now writes the
whole page -- `<head>`, `<body>`, the return link, the interleaved notes and the correlation
paragraphs -- so regenerating is lossless and reproducible. The prose lives in the `.py` files
now, which is where it must be edited; editing the `.html` directly will be overwritten on the
next run. Still diff against `git show HEAD:<path>` after regenerating to confirm only what you
intended changed.

Related: the committed HTML pins the CDN to `plotly-3.5.0.min.js` with an SRI `integrity` hash, but
the installed plotly is 6.6.0 -- regenerating changes both the URL and the hash. That is expected;
just never hand-patch one without the other.

### 1. Replace the "click a link to leave the page" navigation with an in-page tab section

Currently `index.html` has three `<a>` links under "Visualization Links" that navigate
the browser away to `lineCharts.html`, `scatterPlots.html`, and `visualizationThree.html`.
Replace this with a tab UI embedded in the landing page: three tab buttons (one per
visualization group), and clicking one displays that visualization's content in a content
area on the same page, without a full page navigation.

**Implementation approach: use `<iframe>` elements, one per tab, toggled via `display: none`/`block` (or a `hidden` attribute) on click.**

Why iframes and not fetch-and-inject: each of the three HTML files independently loads
the Plotly CDN script and contains its own inline `<script>` tags that build the charts.
Injecting raw fetched HTML into a `<div>` via `innerHTML` does **not** execute embedded
`<script>` tags — you'd have to manually re-create and re-insert each script node, and
guard against loading the Plotly CDN script multiple times into the same document,
which is extra complexity this project doesn't need. Iframes sidestep all of that: each
one is its own document context, so the existing files work completely unmodified.

Concrete requirements:
- Three tab buttons with clear labels, e.g. "Trends Over Time" (→ `lineCharts.html`),
  "Income vs. Turnout" (→ `scatterPlots.html`), "2024 Snapshot" (→ `visualizationThree.html`).
  Adjust wording if you find clearer labels, but keep them short (2-4 words) — these
  are UI tab labels, not the old link text.
- Only one tab's iframe is visible at a time; switching tabs must not cause a full page
  reload (use `iframe.src` set once on first activation — lazy-load — or set upfront;
  either is fine, but don't reload an iframe's `src` every time its tab is reselected).
- Each iframe needs a **fixed height with internal scrolling**, not an auto-sized height —
  the underlying pages stack 2-3 Plotly charts each and get tall (roughly 900-1600px
  depending on the page). Use something like `height: 75vh; width: 100%; border: none;
  overflow: auto;` on each iframe so switching tabs doesn't cause the whole landing page
  to jump/reflow. Test this and adjust the exact height if charts get cut off or leave
  excessive empty space.
- Keep the first tab active/visible by default on page load.
- Make sure this still works when the site is served over GitHub Pages (https) — it will;
  just don't rely on anything that only works over `file://`. Test locally with
  `python -m http.server` from the repo root, not by double-clicking `index.html`.

### 5. Add a computed Pearson correlation coefficient

The site currently *asserts* relationships ("no strong correlation between race and
income," specific percentage-point gaps) based on eyeballing the charts, with no
statistic backing them up. Add real `scipy.stats.pearsonr` computations, but **decide
per visualization group whether a coefficient is meaningful and where, if anywhere, it
belongs** — don't mechanically bolt one onto every chart. Specifically:

- **`visualizationOne` (line charts) / `visualizationTwo` (scatter plots):** both are
  built around the continuous relationship between median income and voting percentage
  across years and race groups — this is the natural place for a Pearson r, since both
  variables are continuous. Compute it on the merged data already being built in
  `visualizatinoTwo.py` (the `combinedDf` dataframe), and surface the result: at minimum
  as a line of text near the relevant chart(s) on the landing page, and consider also
  adding it as a chart subtitle/annotation via Plotly if it's not too cluttered. Decide
  whether one pooled coefficient across all races/years is the right summary, or whether
  per-race coefficients are more honest given the page's own claim that the relationship
  changes once race is factored in — lean toward whichever is more statistically honest,
  even if it means showing more than one number.
- **`visualizationThree` (bar charts):** the x-axes here (`Income Amount`, `Income Range`)
  are categorical bins (e.g., "Under $15,000," "$150,000 to $199,999"), not continuous
  values. Running `pearsonr` directly against bin labels is invalid. If you want a
  coefficient here, you'd need to convert each bin to a numeric proxy (e.g., bin
  midpoint, with the open-ended top bin handled explicitly) — that's a legitimate but
  debatable methodological choice, so if you do it, say so explicitly in the text next to
  the number (e.g., "using income-bracket midpoints as a numeric proxy"). It's also
  reasonable to conclude a correlation coefficient doesn't add value for this
  particular chart and skip it — that's an acceptable outcome of this task, not a
  failure to complete it.
- After editing `visualizationOne.py` / `visualizatinoTwo.py` / `visualizationThree.py`,
  you must **re-run each script from inside its own directory** (they use relative paths
  like `../data/...`) to regenerate the corresponding `.html` file, e.g.:
  ```
  cd visualizationTwo && python visualizatinoTwo.py
  ```
  Confirm `scipy` is installed (`pip install scipy` if not) before running.
  Regenerating overwrites the hand-authored `<head>`/`<body>` wrapper, return link, and
  interleaved commentary in each `.html` — see "The generated HTML files are hand-edited
  after generation" above and restore them afterwards.
